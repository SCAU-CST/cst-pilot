# 接收端

状态：草案，尚未开始设计。更新：2026-09-16。字段见 [schema.md](schema.md)。

## 结论

1. 第一版只做两件事：收记录，写数据库。看板与告警后置。
2. 一场会话一条记录，原始记录整体存 JSON，不拆明细表。
3. 部署在队伍自己的服务器或云主机，不引入第三方 SaaS。
4. 不做用户管理，身份靠指纹映射表维护。

## 接口

```
POST /v1/sessions
Authorization: Bearer <上传凭据>
{ "v": 1, "batchId": "<uuid>", "sentAt": "...", "records": [ ... ] }
```

| 响应 | 发送端行为 |
|---|---|
| 202 `{ accepted, rejected }` | 整批算成功，不重发 |
| 400 / 403 / 413 | 丢弃该批 |
| 429 / 5xx | 落盘重试 |

约定：单批上限 50 条或 1 MB；逐条校验，非法条目进 `rejected`，不拒绝整批；接收时间与来源 IP 由服务端补充；`GET /healthz` 返回进程与数据库状态。

去重方式见议题 R15。

## 存储

| 表 | 主键 | 内容 |
|---|---|---|
| `installs` | `install_id` | 首次与最近上报、系统与版本 |
| `members` | `key_fp` | 指纹到队员的映射，人工维护 |
| `sessions` | `record_id` | 会话记录。公共字段建列，`models[]` 与 `tools[]` 进 JSON 列 |
| `daily_rollup` | `(date, key_fp)` | 每日聚合，报表只读这张表 |
| `upload_log` | `batch_id` | 批次去重与来源 IP，按保留期清理 |

`members` 不做外键强制，未登记指纹照常入库，报表归入「未映射」，避免丢数据。

## 选型候选

| 方案 | 优点 | 代价 |
|---|---|---|
| A 单进程 + SQLite | 部署最简，备份即拷文件 | 数据量大后查询变慢 |
| B Postgres + 看板 | 查询强，看板现成 | 运维成本高 |
| C Serverless + 托管库 | 免运维 | 依赖第三方 |
| D 只落 JSONL 文件 | 实现最快 | 无查询能力 |

建议先做 A，接口与表结构按本文件设计，需要时换 Postgres。最终见议题 R2。

## 报表需求

每人每日 token 与费用、模型使用分布、工具调用次数与失败率、会话数与时长、版本与系统分布、来源地区。先做哪些见议题 R3。

## 安全与运维

| 项 | 要求 |
|---|---|
| 传输 | 只用 HTTPS |
| 鉴权 | 上传凭据不等于模型 KEY，方式见议题 R4 |
| 限制 | 请求体上限 1 MB，按安装标识限流 |
| 写入 | JSON 入 JSON 列，不拼 SQL |
| 保留期 | 记录与批次日志到期删除，见议题 R5 |
| 删除 | 支持按安装标识或指纹删除该来源全部数据 |
| 备份与监控 | 定期备份数据库；监控进程存活、磁盘水位、请求失败率 |

记录里不含机主路径与对话内容，但仍可推断使用习惯，保留期与访问范围需明确规则。
